# One Image, One Story：生成与自动发布系统设计

日期：2026-09-08  
状态：已完成方案讨论，等待用户审核设计文档

## 1. 目标

建立一套可重复使用的“一图一文”创作与分享闭环：用户向 Codex 提供一句主题、一段文章或一个网页 URL，Skill 自动提炼观点、生成纯视觉配图与独立短文，校验成功后提交到公开 GitHub 仓库，并由 GitHub Pages 自动发布。用户可以在瀑布流首页浏览全部作品，也可以分享任意作品的永久独立链接。

首版以低维护、可审计、可迁移为优先级，不建设后台、数据库、账户系统或在线编辑器。

## 2. 已确认的产品决策

- 发布方式：生成完成并通过自动校验后立即提交、推送和部署，不逐篇等待人工确认。
- 输入范围：同时支持主题、文章文本和网页 URL。
- 图文关系：图片为纯配图，不嵌入标题或正文；文字作为独立可复制、可搜索的内容。
- 浏览方式：响应式瀑布流首页，每篇内容拥有独立页面和永久链接。
- 视觉策略：统一品牌风格为主，允许根据主题微调主体、配色和氛围。
- 仓库：新建公开仓库 `one-image-one-story`，使用 GitHub Pages 分享。
- 技术方案：Astro 静态站点 + Markdown 内容集合 + GitHub Actions Pages 部署。
- 首个样例：《Figwright：免费的 Figma MCP》。
- 推荐说明：首个样例发布后，再生成一篇解释视觉、内容与技术选择的推荐文章，供用户检查。

## 3. 方案选择

### 3.1 推荐方案：Astro 静态站

Astro 在构建时把 Markdown 转成真实 HTML 页面，适合内容型站点。它可以为每篇作品输出独立路径、标题、摘要、图片与 Open Graph 元数据，兼顾 GitHub Pages、搜索引擎、社交分享和低运行成本。页面发布后不依赖数据库或服务端。

### 3.2 未采用方案

- 原生 HTML/JS + JSON：依赖更少，但独立页面、SEO、分享预览和内容校验都需要自行补齐。
- Next.js + Vercel：能力充足，但首版没有服务端需求，也偏离用户希望以 GitHub 为中心的目标。

## 4. 系统组成

### 4.1 `one-image-one-story` Skill

Skill 安装在 Codex 的个人 Skills 目录，对以下表达自动触发：生成一图一文、把主题做成图文卡片、把文章或网址整理成一图一文、发布一篇图文。

职责边界：

1. 判断输入类型并取得源内容。
2. 提炼一个核心观点，生成标题、150–300 字中文短文、标签、图片替代文本和图片提示词。
3. 调用图像生成能力生成 4:5 纯配图。
4. 将正文和元数据写成 Markdown，将图片写入仓库资源目录。
5. 调用仓库脚本完成内容校验、静态构建、提交、推送和部署验证。
6. 返回作品页面与站点首页链接。

Skill 不负责实现网站渲染，不在指令中复制构建逻辑；这些能力归仓库脚本所有。

### 4.2 内容仓库

仓库保存站点代码、内容和图片，是唯一发布源。建议结构：

```text
one-image-one-story/
├── src/
│   ├── components/
│   ├── content/
│   │   ├── config.ts
│   │   └── posts/
│   ├── layouts/
│   ├── pages/
│   └── styles/
├── public/
│   └── images/posts/
├── scripts/
│   ├── validate-post.mjs
│   └── publish-post.mjs
├── tests/
├── .github/workflows/deploy-pages.yml
└── docs/
```

### 4.3 GitHub Pages

向 `main` 分支推送后，GitHub Actions 安装依赖、运行校验和构建，将 Astro 产物部署到 Pages。站点地址根据发布时登录的 GitHub 账户与仓库名自动确定，Astro 的 `site` 和 `base` 在发布配置中同步写入。

## 5. 内容模型

每篇作品使用一个 Markdown 文件，正文是最终短文，frontmatter 至少包含：

```yaml
title: string
slug: string
publishedAt: ISO date-time
summary: string
image: /images/posts/figwright-free-figma-mcp.png
imageAlt: string
tags: string[]
sourceType: topic | text | url
sourceUrl: string | null
status: published
```

约束：

- `slug` 全局唯一、只用小写英文、数字和短横线。
- 图片必须存在，建议尺寸为 1600×2000 或等比例 4:5 PNG。
- 图片中不生成标题、正文、Logo、水印或仿冒商标。
- 短文必须可以脱离源文独立阅读；若输入是文章或 URL，不逐段改写，而是提炼单一观点。
- 原始来源 URL 在独立页中明确展示；没有 URL 时不渲染来源区域。

## 6. 视觉与交互设计

品牌基调为“编辑部档案 × 当代数字画册”：温暖浅色纸张背景、深墨色正文、一种高识别度强调色、克制的细线和编号系统。图片保持统一的摄影棚光线、精致材质和清晰主体，但根据主题调整物件、场景和辅色。避免把所有题材强行生成同一种科幻界面。

首页：

- 桌面端 3–4 列瀑布流，移动端单列。
- 卡片突出 4:5 图片，下方显示标题、短摘要、日期和标签。
- 图片加载时保留比例，避免布局跳动。
- 新内容按发布时间倒序排列。

独立页：

- 大图、标题、正文、来源与标签形成单一阅读路径。
- 提供复制链接和返回首页操作。
- 输出完整 Open Graph 与 Twitter Card 元数据，分享时优先显示作品图片。

## 7. 生成与发布数据流

1. 用户输入主题、文章或 URL。
2. Skill 获取并规范化源内容；无法读取 URL 时停止，不伪造摘要。
3. 生成结构化文案草稿与图片提示词。
4. 生成图片并检查文件存在、尺寸与格式。
5. 计算 slug，写入 Markdown 和图片。
6. `validate-post.mjs` 校验 schema、字数、来源、slug、图片引用和重复项。
7. 运行站点测试与 `astro build`。
8. `publish-post.mjs` 只暂存本次新增的文章和图片，创建清晰提交并推送 `main`。
9. 等待 GitHub Pages 工作流完成，验证首页和独立页可访问。
10. 向用户返回两个链接；部署失败时返回失败阶段与 GitHub Actions 链接。

## 8. 自动发布与安全边界

“自动发布”只覆盖公开、非敏感内容的正常路径。以下情况必须停止，不提交、不推送：

- 输入明显包含密钥、私人对话、内部文档、个人身份信息或未授权素材。
- URL 无法读取、正文为空或内容提炼缺少证据。
- 图片生成失败、尺寸错误、包含明显乱码文字或与主题无关。
- Markdown schema、静态构建或测试失败。
- 当前工作区存在会被本次提交意外包含的无关修改。

如果推送失败但本地提交成功，保留本地提交并明确报告；不得声称已经发布。GitHub Actions 失败时不重复创建文章，而是修复同一提交链路。

## 9. 测试与验收

### 9.1 Skill

- 主题、文章文本、URL 三种输入各执行一个代表性测试。
- 验证输出包含 Markdown、4:5 图片、来源信息和可访问链接。
- 验证敏感或不可读取输入会停止发布。

### 9.2 内容与站点

- schema 校验：必填字段、类型、唯一 slug、正文长度、图片路径。
- 构建校验：`astro build` 无错误，首页和独立页均被输出。
- 页面校验：桌面与移动端布局、图片比例、复制链接、返回导航和来源链接可用。
- 分享校验：独立页包含正确的 canonical、Open Graph 标题、描述与图片。
- 部署校验：GitHub Actions 成功，Pages 首页和两篇首发内容返回成功状态。

### 9.3 首次交付物

1. 可自动触发的 `one-image-one-story` Skill。
2. 公开 GitHub 仓库及中英文 README。
3. 已部署的 GitHub Pages 站点。
4. 《Figwright：免费的 Figma MCP》一图一文样例。
5. “一图一文的视觉与内容推荐”说明文章。
6. 首页、独立页、移动端和分享元数据的验证证据。

## 10. 非目标

首版不包含在线登录、浏览器内编辑、评论、点赞、数据库、定时抓取、多语言内容、付费功能、第三方分析或自定义域名。这些能力只有在真实使用证明有必要时再增加。
